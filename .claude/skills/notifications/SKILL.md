name: notifications
description: Reference for the bell-icon notification center (resurfaced-domain and due-date-reached events), backed by Redis + asynq, spanning internal/notify/, db.Notification, internal/server/handlers.go, and web/src/components/notification-bell.tsx. Use when working on notifications, due-date scheduling, or resurfaced-domain alerts.
---


- A bell-icon notification center covering two event types, both backed by Redis + [`hibiken/asynq`](https://github.com/hibiken/asynq) rather than a plain DB-polling sweep, chosen for precise per-domain due-date timing (some SLAs are hours, not "whenever the next periodic sweep runs") plus built-in retry/scheduling. The asynq worker + scheduler run embedded inside `cmd/server` as extra goroutines (`notify.Server`, started/stopped alongside `StartScheduler`/`StartWhoisRefresher` in `main.go`) — no third binary. See `docs/superpowers/specs/2026-08-04-notifications-design.md` for the full design rationale.
- **Producer 1 — resurfaced domains** (`notify.Server.handleResurfacedSweep`, a periodic asynq task registered at a fixed `@every 15m`, no admin setting): iterates every department, reuses `store.ResurfacedDomainsForDepartment` (see "Resurfaced domains" above), and inserts a `db.Notification{Type: "resurfaced"}` row per (department, url) not already notified for that specific resurface event — deduped via `store.HasRecentResurfacedNotification` (an existing row's `CreatedAt` at/after the resurface's `ResurfacedAt` means it was already reported).
- **Producer 2 — due-date reached** (`notify.Enqueuer.RescheduleDueDate`, called from `PATCH /api/urls/{id}` in `internal/server/handlers.go`'s `ToggleURL` whenever `URL.DueDate` changes, and from `RemoveFromWatchlist` on removal): deletes any previously-scheduled task for that `(department, url)` pair (deterministic `asynq.TaskID` = `due:<department_id>:<url_id>`) then, if the new date is non-nil and in the future, enqueues a one-shot task via `asynq.ProcessAt`. Clearing the date or removing the watchlist entry just deletes, without a replacement. `DueDate` is global on the `URL` row (shared across every department watching it — see "Domain normalization & watchlists" above), so `ToggleURL` fans a change out to every department watching that URL (`store.DepartmentIDsWatchingURL`, regardless of that department's own `Enabled` flag), not just the one that made the `PATCH` call — each watching department gets its own scheduled check and, later, its own `db.Notification` row. `RemoveFromWatchlist`, by contrast, only cancels the *calling* department's own task, since removing yourself from a watchlist doesn't change the shared `DueDate` or other departments' interest in it.
- When a due-date task fires (`notify.Server.handleDueDateCheck`): calls `Scanner.Trigger(ctx, "due-date-check", []string{url})` (the same targeted-scan mechanism "Scan Selected"/`TriggerScreenshot` use), polls `Triggerer.IsRunning()` until the scan completes, reads the resulting `ScanResult` rows via `store.ResultsByURL`, and inserts one `db.Notification{Type: "due_date_reached", Compliant: <all servers compliant>, Details: <per-server breakdown>, ScanRunID, ScannedAt}` row. asynq's default retry (bounded exponential backoff) covers transient failures, including `Scanner.Trigger` returning "scan already in progress."
- `db.Notification` (`department_id`, `url_id`+`url_value` — mirroring `ScanResult`'s dual FK+denormalized-value pattern, `type`, `compliant` nullable, `details` jsonb, `read_at`, `created_at`, indexed on `(department_id, read_at)`) also carries `ScanRunID *uint`/`ScannedAt *time.Time` recording which scan produced the notification: `due_date_reached` always sets both (one targeted `Trigger` call is always exactly one `ScanRun`, so all its `results` share a `ScanRunID` — `handleDueDateCheck` takes `results[0].ScanRunID` and the latest `ScannedAt` across servers); `resurfaced` sets only `ScannedAt` (the flip time, `ResurfacedDomain.ResurfacedAt`) since a resurfacing event can span servers checked in different scan runs, so there's no single run to attribute it to. Exposed via `NotificationStore` — `GET /api/notifications` (paginated, admin-global/department-scoped like `/api/resurfaced`), `GET /api/notifications/unread-count`, `PATCH /api/notifications/{id}/read`, `DELETE /api/notifications/{id}` (dismiss one), `DELETE /api/notifications` (bulk-dismiss — `ClearAllNotifications`/`ForDepartment`, same admin-global/department-scoped split as the list/count routes, so it clears everything the caller can see, not just the dropdown's first page; the department-scoped delete uses a `department_id = ?` WHERE, the global one a literal `1 = 1` since GORM refuses a conditionless bulk delete outright) — the single-notification routes 404, not 403, for another department's notification (`requireDomainOwnership`'s pattern; `Handlers.ownedNotificationID` is the shared ownership-check helper both call).
- Frontend: `web/src/components/notification-bell.tsx` (`NotificationBell`) — a bell icon (`web/src/components/ui/bell.tsx`'s `BellIcon`, vendored from the `@lucide-animated` shadcn registry — `npx shadcn@latest add @lucide-animated/bell` — an SVG that wiggles on hover; sized at 18px to match the navbar's other `IconBarItem` icons, e.g. "Scan All") + unread badge mounted in `glass-navbar.tsx`'s actions slot via `__root.tsx`, polling `GET /api/notifications/unread-count` every 30s (same lightweight pattern `scan-results.tsx` uses for scan status) and opening a small dropdown (`GET /api/notifications`, first page) on click. A "Clear all" button sits above the list (only rendered when there's at least one notification) calling `clearAllNotifications`, optimistically emptying the list and zeroing the badge, rolling back via a fresh `refreshCount()` on failure. Each row below it is a flex pair: a content button — domain, message, and a `Scan #<id> · <relative time>` line (the `Scan #` prefix omitted when `scan_run_id` is absent, i.e. every `resurfaced` notification and any `due_date_reached` row from before this field existed) — clicking it marks the notification read and navigates to `/domain/$url?tab=history&run=<scan_run_id>` (deep-links into the History tab, auto-expanding and scrolling to that scan run if `scan_run_id` was set — see `domain.$url.tsx`'s `run` search param below); and a dismiss (×) button calling `deleteNotification`, optimistically removed from the list with `stopPropagation` so it doesn't also trigger the row's navigate. `web/src/api/notifications.ts` owns the five fetchers (`fetchUnreadCount`/`fetchNotifications`/`markNotificationRead`/`deleteNotification`/`clearAllNotifications`).
- `domain.$url.tsx`'s `run?: number` search param (alongside `tab`/`server`) is deep-linked from the notification bell: once scan results load, a `useEffect` finds the matching group in the History tab's `groups` list, jumps `page` to the page containing it, adds it to `expandedRuns`, and scrolls `#scan-run-<id>` into view — guarded by a `jumpedToRun` ref so it fires once per `run` value even if the user manually re-collapses the row afterward.
- Out of scope for now: per-user notification preferences, email/Slack delivery, an admin-configurable resurfaced-sweep interval, and real-time (SSE) push — the badge is polling-only.
